# 三人协作入口

先让三个人在各自机器完成 README 的安装、测试和 demo，再提交第一个小 PR。无需安装上游所有训练依赖；本项目的基础拍卖回放与可选 PPO 环境分开使用。

## 工作方向

| 角色 | 主要目录 | 优先交付 | 合并前共同核对 |
| --- | --- | --- | --- |
| 实习生 A：数据与预测 | `src/autobid/data.py`、`adapters.py`、数据卡和分析脚本 | 获取一份真实 AuctionNet 投放期；核对字段、ID 和顺序；按角色统计有效机会与潜在价值；建立按整日划分的同时段均值预测 | 不能跨请求拼参与者；缺失配对不补零；预测特征不使用未来 |
| 实习生 B：环境与评估 | `engine.py`、`policies.py`、评估入口和 `tests/` | 手工复核拍卖；跑固定系数和本地 pacing；比较预算紧张程度；整理回放与资源耗时 | 单槽二价、预算、并列和空片；对手每局实际更新 |
| 负责人：策略与审查 | `rl.py`、`submission.py`、配置和评估结论 | 确认官方边界规则；冻结状态/奖励；审查训练和独立加载；选择下一轮预测、优化或 RL 改进 | 信息边界、数据划分、目标一致性、实验可复现 |

Pacing 是工程对照，不是团队主要算法方向；后续优化/RL 是否有价值由独立验证决定。A、B 共享数据和环境测试样例，避免在两条线上分别发明一套规则。

## 每次开发

```bash
git switch main
git pull --ff-only
git switch -c feature/describe-one-change
```

完成一个明确变化后运行测试，提交代码并创建 PR。PR 写清楚问题、改动、运行命令和结果；若改动了规则、数据含义或在线特征，负责人先看对应样例。首次协作只需普通 feature 分支，不需要长期维护多套 dev 分支。

提交小型人工/合成样例、配置、测试和文档；原始大数据、模型权重、实验日志放在被忽略的目录中，并在实验记录里保存可获取的路径、数据哈希和模型标识。不要将 API key、账号信息或正式隐藏测试数据提交到仓库。

## 首轮待办

- A：下载一个真实上游投放期，记录下载来源与数据条件；用小规模完整请求抽样验证适配器，再核对全期统计与预算尺度。
- B：将三个手算请求与环境 audit 对照；补上正式 SDK 发布后的预算不足、零预算、舍入与同价规则用例。
- A + B：准备至少两个不同完整日期/源投放期，分别作为训练和验证；严禁把同一日的行随机拆散。
- 负责人：用固定策略和 pacing 对照验证 PPO 保存与新进程加载；多随机种子比较，不能凭短训练 reward 上升判定有效。
- A：训练片前可用的供给预测；只将训练期拟合的预测器及预处理保存，下一片真实机会数只能作标签。
- B + 负责人：增添不同策略同场的角色轮换、异常计数和符合正式统计口径的延迟/内存测量。

## 正式数据到来时

先检查六字段、时间起点、请求作用域、参与关系、价值尺度和角色预算；再检查官方动作边界、预算处理、同价与金额精度。通过手工样例后跑同一套 baseline 和模型训练入口，按完整验证日选模型。最后在独立进程加载封存模型，核对所有 72 片和资源限制。

不要等待正式数据才第一次跑训练；准备阶段要知道一次回放和一次短训练耗时。保留可运行的固定系数回退方案，但不要把本地对照基线称为主办方 PID。

## 仓库权限

仓库保持私有。两位实习生需要各自 GitHub 账号及仓库 Write 权限才能推分支和提 PR。邀请由仓库管理员在 Settings → Collaborators 中添加；本次初始化没有猜测账号或发送邀请。GitHub Actions 工作流是检查入口，是否设为强制合并条件由管理员在分支规则中配置。
